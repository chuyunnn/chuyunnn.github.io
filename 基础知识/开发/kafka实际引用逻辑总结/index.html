具体怎么把数据从消息队列中拿出来，怎么消费？

这个流程有几个部分：
分片校验、分片上传、minIO存储分片信息并合并、sql存储文件元数据信息（不是分片）

存储路径设置：storagePath = “chunks/“ + fileMd5 + “/“ + chunkIndex;

🌟 首先让我们明确kafka里面存储的都是什么数据：

元数据，主要告诉消费者可以去哪里找这些数据：MD5、一共有多少分片、合并之后存在哪里

🌟 然后让我们明确kafka是在哪个步骤解耦的：

[!NOTE]

分片数据（File Chunks）的数据流转过程：前端 -> 后端服务 -> MinIO 临时目录。

  • 步骤 A（写入）：前端每上传一个分片，后端接收到二进制流后，立即将其写入 MinIO。

  • 存储规则：按文件 MD5 划分文件夹。例如s3://temp-bucket/md5_abc123/chunk_0, chunk_1…

  • 步骤 B（驻留）：这些分片在 MinIO 的临时目录下静静地躺着，直到所有分片上传完毕。

  • 步骤 C（合并）：当收到合并指令时，MinIO 在服务端内部将这些分片拼成一个大文件，移动到正式目录。

关键点： 分片数据从头到尾都没进入过 Kafka，甚至在“合并”阶段，数据都不会流经你的后端服务 CPU（利用 MinIO 的 composeObject 接口）。

⚠️ 你也可以用kafka也解耦分片上传流程，但是这样的话kafka就要存储分片数据。但是kafka擅长处理高吞吐的小消息，这样会导致一些内存浪费（minio和kafka存储了两份数据、消费需要开销）和kafka性能下降。

🌟 分片校验、上传是在哪里做的？

  1. 校验是“上传分片”的 Controller/Service 层同步做，而不是在 Kafka 消费者里做。

流程：前端发送 -> 后端接收 -> 将计算的MD5和前端传来的chunkHash比对（分片md5） -> 校验通过就写入minio -> bitmap位图记录

总结：是同步做的 ==> 如果分片损坏，后端必须立刻返回 400 或 500 错误码，前端收到后才能触发自动重试逻辑。如果进了Kafka再发现坏了，后端很难主动触达前端要求重传。

⚠️ 实际代码没有立即对分片进行校验

  1. 上传分片：上述逻辑

🌟 总结kafka具体解耦的部分：「IO密集型的分片接收」和「计算密集型的文件处理，即后续分片合并、数据写sql逻辑」解耦

如果不用kafka：需要等文件合并、embedding之后才能返回，一直转圈，而用kafka可以只等分片上传部分

因此，kafka只传输一些文件元数据的json信号，后续service取数据进行处理

🌟 kafka消费流程：

  • 幂等性校验：先去sql查一下文件md5对应的记录状态，是否为已合并，如果是就跳过下述逻辑
  • 调用minIO的composeObject功能，在minIO服务端完成分片合并
  • 在sql中插入文件记录，记录文件对应的基本元信息，并且建立了文件分片表，可以记录分片文件元信息
  • 异步删除 Redis 里的 BitMap 和 MinIO 里的临时分片目录，释放空间

🌟 kafka有多个消费者，如何保证消费顺序？

1. 单一消费者组 + 顺序执行（最推荐，简单可靠）

在文件处理这个场景下，逻辑是有严格先后顺序的。你不能在还没合并完文件时就去写 SQL（因为不知道最终路径），更不能在合并完之前就删掉临时目录。

具体做法： 定义一个 FileProcessorConsumer，在它的 onMessage 方法里按照业务逻辑编写同步代码。手动提交 Ack，告诉 Kafka 这条消息处理完了。

  • 优点：自然保证了顺序性。任何一步报错，整个消息都会重试，保证了原子性。
  • 适用场景：这些逻辑属于同一个微服务（文件服务）时。
2. 多消费者组 + 订阅模式（解耦不同服务：文件合并由文件服务做，向量化由AI服务做）

在 Kafka 中，只要给不同的服务设置不同的 group.id（消费者组 ID），Kafka 就会把同一条消息分发给每一个组。保证顺序有三种策略：

  • 策略 A：链路传递（消息链）

文件服务消费消息 A（开始合并) -> 合并完后，文件服务往另一个 Topic 发送消息 B（合并完成） -> AI 服务消费消息 B（开始向量化）。

  • 优点：完全解耦，每个服务只管自己的事。

  • 策略 B：状态驱动（最佳实践）

所有服务都消费同一个 Topic，但通过 MySQL 的文件状态字段来控制。

  • AI 服务拿到消息后，先查 SQL：status 是不是“已合并”？如果不是，说明文件还没准备好，此时可以选择 pause 消费或者等待重试。

  • 策略 C：工作流引擎（如 Temporal 或 Airflow）

对于非常复杂的长链路任务（上传-合并-审核-向量化-分发），通常会引入工作流引擎来编排顺序，而不是纯靠消息队列硬扛。

kafka消息可靠性传递、消息重试机制

消息可靠性机制：

  1. 生产者端：设置了 acks=all，也就是生产者发送一条消息，必须等到所有同步副本都写成功，才算这条消息真正发出。这是 Kafka 提供的最高级别可靠性设置，哪怕 leader 写完之后宕机了，只要 follower 写成功了，就不影响消息落盘，避免了“刚写完就丢”的风险。
  2. 服务端：把 topic 的副本数设成了 3，也就是一个 leader + 两个 follower，再加上配置了 min.insync.replicas=2，意思是如果只有一个副本存活了（比如只有 leader 没挂），Broker 就会拒绝写入请求。这个机制相当于在服务端也加了一道“健康检查”，防止我们写入到一个马上就挂掉的分区上，避免数据丢失。
  3. 消费者端：手动ack提交。设置了 enable.auto.commit=false 转为手动提交。这样能确保只有当我们的业务逻辑真正执行成功，比如向量写入 ES 成功，数据库状态更新成功，才会调用 commitSync() 提交 offset。这样即使系统崩溃，重启后还能从失败点重新拉取任务，保证至少处理一次，不会丢任务。

消息重试机制：

  1. 生产者端：Kafka 的 retries 参数设置了 3，当生产者发送消息失败时，它会自动尝试重新发送，最多 3 次。同时， enable.idempotence: true 的配置也能确保即使在重试过程中，消息也只会被写入一次，避免了因重试导致的数据重复问题。
  2. 消费者端：通过 DefaultErrorHandler 实现了一套优雅的消费者重试与死信队列机制。FixedBackOff 会阻塞当前消费线程 ，等待 3 秒后进行第一次重试。如果再次失败，它会再等 1 秒，进行第二次重试，总共最多重试 4 次【加上第一次一共五次】。如果 4 次后仍然失败， DeadLetterPublishingRecoverer 会接管这个消息，将它发送到死信队列中 （在项目中是 file-processing-dlt）
