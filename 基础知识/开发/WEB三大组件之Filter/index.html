基本定义

Filter，过滤器，属于Servlet规范，并不是Spring独有的

作用：拦截http请求，做一些业务逻辑操作

一个http请求过来之后，一个Filter的工作流程：

  • 首先**进入filter，执行相关业务逻辑**
  • **若判定通行，则进入Servlet逻辑，Servlet执行完毕之后，又返回Filter**，最后在返回给请求方
  • 判定失败，直接返回，不需要将请求发给Servlet

所以可以用filter来实现用户身份识别（获取、校验），然后将识别的用户信息保存到TreadLocal对应的上下文中，这样在后续的请求链路中任何地方都可以直接获取当前登录用户

使用

实现Filter接口即可

eg：输出请求日志的拦截器

  • 在doFilter方法中添加业务逻辑

  • 如果允许访问继续，则执行chain.doFilter(req, response);，如果不执行上面这一句，则访问到此为止

注册

WebFilter注解

将@WebFilter标注到自己实现的过滤器上（上述例子中的ReqFilter），其中参数配置：

参数名 类型 核心作用 是否必填
filterName String 过滤器名称，用于在多过滤器时区分不同FIlter，或者配合@WebFilter排序 否
value/urlPatterns String[] 【最常用】指定过滤器拦截的 URL 路径（拦截所有/某路径下/以xx为后缀/精准拦截） 是（二选一）
servletNames String[] 精准拦截指定名称的Servlet处理的请求，不是所有url 否
dispatcherTypes DispatcherType[] 指定拦截的请求类型（如请求、转发、包含等） 否（默认 REQUEST）
asyncSupported boolean 是否支持异步请求（如果拦截的servlet是用来异步处理，那Filter也必须开启） 否（默认 false）
initParams WebInitParam[] 过滤器初始化参数 否
description String 过滤器描述信息（纯注释性参数） 否
displayName String 过滤器展示名称（纯注释性参数） 否

🌟 使用这个注解的时候需要在启动/配置类上添加@ServletComponentScan注解来启用

FilterRegistrationBean

@WebFilter指定filter优先级比较麻烦，不如FilterRegistrationBean简单

实例：实现请求日志记录

实现功能：将所有外部访问都记录在日志文件中

  • 基于日志文件就可以实现整个项目的监控
  • 出现问题的时候可以基于此进行流量重放

而过滤器Filter可以拦截web请求，其doFilter方法可以划分为三块：

  • doBefore：表示将请求转发到 Controller 执行之前
    • 记录开始执行时间
    • 记录请求相关信息
  • doFilter：即将请求转发到 Controller 去执行
  • doAfter：**Controller 方法执行完**
    • 记录结束时间，计算执行耗时
    • 日志输出

使用Filter做日志记录的优点是适用性强，实现简单，缺点是只能记录 Controller 的请求相关信息，如果我们想统计某个 Service 方法、Mapper 方法，那么这种方式则不太合适

==> 还可以用AOP的方法，但这就要自己定义切点什么的了

核心逻辑还是「请求前处理 → 放行请求 → 请求后处理」

1. 基础配置

2. 核心方法 doFilter（请求处理的主流程）

  • 请求前处理阶段

initReqInfo()：核心初始化方法

CrossUtil.buildCors()：处理跨域（比如前端访问后端接口时的跨域问题，过滤器统一处理）

filterChain.doFilter()：放行请求 → 这行代码执行后，才会走到 Controller 的接口方法

  • 请求后处理阶段finally块，无论是否异常都会执行

buildRequestLog()：核心日志构建方法

stopWatch.prettyPrint()：打印每个步骤的耗时（比如开发环境能看到 “请求参数构建用了 3ms，业务执行用了 50ms”）

isStaticURI()：判断是否是静态资源（css/js/png 等） ==> 这里pc前台的网页也集成在项目中，所以需要排掉静态资源

3. 辅助方法拆解

  1. initReqInfo()：请求上下文初始化

==> 给每个请求初始化「链路追踪 ID、用户信息、设备 ID、请求基本信息」，并存入ReqInfoContext（线程上下文），后续业务代码可直接获取这些信息

getOrInitDeviceId()：生成 / 获取设备唯一 ID（Cookie 存储），用于统计 UV（独立访客）

wrapperRequest()：包装 POST 请求，读取请求体（JSON 参数）并存入 reqInfo，方便日志记录

AsyncUtil.execute()：异步执行 PV/UV 统计，避免统计操作阻塞请求响应

  1. buildRequestLog()：构建并输出请求日志

==> 把请求的核心信息（方法、IP、用户 ID、URL、参数、耗时）拼接成日志，输出到REQ_LOG

传入的时候也是传入request ==> 直接从request里面取日志信息

  • 也就是上面还包含了很多Filter做的，但是和日志无关的功能

扫盲：

  1. ReqInfoContext：线程级别的上下文，用ThreadLocal实现，存当前请求的所有信息，后续Service/DAO层可直接获取（比如获取当前登录用户 ID）
  2. MDC：日志链路追踪工具，给每个请求加唯一traceId，所有日志都带这个ID，排查问题时能快速定位一个请求的所有日志
  3. StopWatch：细粒度计时，方便开发 / 测试环境分析请求耗时瓶颈（比如 “业务执行用了100ms，参数构建用了5ms”）
  4. 异步执行：PV/UV统计用AsyncUtil异步执行，避免统计操作拖慢请求响应

上下文：当前代码执行时的所有环境信息的集合

1. 请求上下文：当前HTTP请求的所有信息的集合
  • 包含请求 URL、客户端 IP、登录用户 ID、设备 ID、请求参数、traceId等等

==> 让整个请求链路（Filter → Controller → Service → DAO）都能直接获取这些信息，不用在每个方法里都传参

比如上述代码中的 ReqInfoContext，就是把当前请求的所有信息存在一个对象里，后续 Service 层想获取 “当前登录用户 ID”，直接 ReqInfoContext.getReqInfo().getUserId() 就能拿到，**不用在每个 Service 方法里都加个 userId 参数**

2. 线程上下文：因为web服务器是多线程的（每个请求都有一个线程），所以请求上下文必须是线程隔离的
  • 用ThreadLocal存储，每个线程有自己独立的上下文，不会互相干扰

典型例子：

  • ReqInfoContext：用 ThreadLocal 存当前**请求**的信息
  • MdcUtil：用 ThreadLocal 存当前请求的**traceId**，保证每个线程的日志都带自己的 traceId

🌟上下文销毁：请求结束后，在 finally 块里调用 ReqInfoContext.clear()，清空当前线程的上下文，避免线程池复用导致数据污染
