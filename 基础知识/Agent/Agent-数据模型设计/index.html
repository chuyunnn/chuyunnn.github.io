Agent-数据模型设计

Created2026-02-27|Updated2026-02-27|基础知识Agent
|Post Views:

Agent中需要持久化的数据可以分成三类：

  1. Agent 与对话状态本身，它们描述的是：谁在和模型交互，这次对话进行到哪一步了。
    • 比如用户 ID、当前对话轮次、当前任务进度等，用来恢复对话上下文
  2. 对话过程中产生的消息记录
    • 用户输入、模型输出、工具执行结果，以及中间的各种元信息
  3. Agent 需要 “按需查阅” 的系统知识。这些知识不属于模型本身，而是通过 RAG 的方式，在需要时提供给模型。
    • AI 在需要时，通过检索增强生成（RAG）技术去查询这些资料，再结合用户问题给出回答

Agent表

在很多简单示例中，Agent 以代码类的形式存在，它的系统指令（system prompt）、可用工具、可访问知识库等核心配置均直接写在代码中，完全依赖开发者手动定义。

==> 当系统规模扩大、Agent 数量增多或需求频繁变更时，硬编码方式会导致「修改成本高、扩展性差、权限与能力边界模糊」，最终引发管理失控

放在一个表里可以：

  • 创建、修改、禁用agent，不需要改代码
  • 系统运行时能够明确：当前agent能做什么不能做什么

这个Agent表描述了：

  • agent是谁：name、description
  • 行为基调：系统指令（行为、角色、任务边界）
  • 能力边界：model、allowed_tools、allowed_kbs、chat_options

[!NOTE]

这里这个chat_options是发给大模型的请求参数，其中：

  • 温度、top_p：控制回答的随机性 / 创造性

  • 最大 token 数：控制回答的长度上限

最终目的：让模型输出更贴合你的业务场景（比如客服场景要严谨，创意场景要灵活）

1. 温度（temperature）—— 控制回答的 “脑洞大小”

温度是一个0~2 之间的浮点数（不同平台上限可能不同，比如 OpenAI 是 02，部分国产模型是 01），核心控制模型输出的随机性和多样性

可以把模型想象成一个 “答题者”：

  • 温度 = 0：答题者极度严谨，只会选 “最可能正确” 的答案，输出固定、无创意，甚至重复
  • 温度 = 1：答题者正常发挥，平衡严谨和创意
  • 温度 = 2：答题者放飞自我，脑洞极大，答案天马行空，甚至可能偏离主题、出现错误

模型生成文字时，会为每个候选词计算 “概率得分”：

  • 温度越低 → 模型越倾向于选概率最高的词 → 输出越固定、保守
  • 温度越高 → 模型会给低概率词更多机会 → 输出越多样、有创意

2. top_p（核采样）—— 控制回答的 “候选词范围”

top_p 是一个0~1 之间的浮点数，也叫 “核采样”，核心是通过 “概率累积” 控制模型可选的候选词范围

模型生成每个词时，会列出所有候选词并按概率从高到低排序：

  • top_p=0.1：只从 “概率累积到 10%（前10%）” 的前几个词里选 → 候选范围极小，输出极固定；
  • top_p=0.9：从 “概率累积到 90%（前90%）” 的词里选 → 候选范围大，输出多样；
  • top_p=1：包含所有候选词 → 等价于不限制范围。

和温度的区别：

  • 温度是 “给低概率词加权”（改变概率分布）
  • top_p 是 “直接筛选候选词范围”（不改变概率，只缩小范围）

⚠️ 重要：不建议同时调整温度和 top_p，选其一即可（行业通用做法是优先调温度，特殊场景再用 top_p）

3. 最大 token 数（max_tokens/max_length）—— 控制回答的 “长度上限”

token 是大模型的 “最小文本单位”（不是汉字 / 单词）：

  • 1 个汉字 ≈ 1 个 token
  • 1 个英文单词 ≈ 1~2 个 token（比如 “hello”=1 个，”beautiful”=1 个）
  • 标点、空格也会占 token

max_tokens 是模型生成回答的最大 token 数量上限（注意：不是 “必须生成这么多”，而是 “最多生成这么多”）

  1. 上下文 token 限制：模型有总 token 上限（比如 GPT-3.5 是 4096，GPT-4 是 8192/128k），这个上限包含 “用户提问的 token + 模型回答的 token”。比如总上限 4096，你提问用了 1000token，那么 max_tokens 最多只能设为 3096（否则会报错）。
  2. 业务成本：token 数越多，调用 API 的费用越高（按 token 计费），同时生成速度越慢。

chat_session 表

关于这个agent和session的对应关系：

  • 一个session对应多个agent：使用多个agent的能力
  • 一个agent对应多个session：多个session复用同一个agent的能力，不用为每个session都创建一个新的agent

一次对话是成一个过程，而不是一次请求，它本身不承载太多信息，只起到一个锚点的作用：把这次对话绑定到某一个 Agent，并为后续所有行为提供归属

  1. 对话是过程，不是单次请求
  • 一次完整的人机交互（比如 “帮我写代码 → 我提修改意见 → 你再改代码”）是一个连续过程，而不是孤立的单次 API 调用
    • 这个过程需要一个 “容器” 来贯穿始终，这就是 chat_session（对话会话）
  1. 会话是 “锚点”，不是信息载体
  • 会话本身不存储具体的聊天内容、工具调用结果等信息，这些都存在后续的消息表（chat_message）里
    • ==> 会话核心作用是锚定归属：
      • 把这次对话绑定到某个特定的 Agent（通过 agent_id 字段）
      • 让后续所有的消息、工具调用、知识库查询等行为，都能明确归属于这一次对话
  1. 设计价值
  • 让系统能清晰地知道 “这条消息属于哪次对话”“这次对话是由哪个 Agent 处理的”，方便上下文管理、历史追溯和权限控制
  • 避免把所有信息都塞到单次请求里，让系统结构更清晰、可维护性更强

chat_message 表

这张表的设计思路非常简单，但非常重要：对对话过程中出现的所有语义片段，都应该是可追溯的。

content 存的是模型真正 “说的话”，metadata 存的是那些不适合直接拼进 prompt，但对系统来说非常重要的结构化信息，比如工具参数、RAG 命中内容、模型选项等。

[!NOTE]

关于为什么要存sql表：

1. 会话中断 / 恢复：解决 “上下文丢失” 问题

模型的 Prompt 上下文是内存级临时数据，如果用户关闭页面、网络中断、服务重启，拼接在 Prompt 里的上下文会直接消失

这是最基础的需求，比如用户问 “帮我调试超分模型”→ 发了报错日志 → 中途退出 → 重新进入后，Agent 能从数据库拉取 “报错日志” 这条消息，无需用户重新发送。

2. 长会话场景：突破模型上下文 token 限制

模型的上下文窗口（比如 GPT-3.5 的 4096 token）是有限的，但用户的对话可能很长（比如聊了 100 轮）

  • 存数据库：可以基于chat_message表做「上下文压缩 / 摘要 / 检索」—— 比如只把和当前问题相关的 5 轮消息（从数据库查）拼接进 Prompt，既满足模型输入要求，又保留关键上下文。

3. 可追溯性 & 审计：满足业务合规 / 问题排查需求

  • 合规要求：金融、医疗、政务等场景，必须留存用户和 AI 的所有交互记录，供监管审计；
  • 问题排查：当 Agent 回答出错时，能从chat_message表查到 “用户输入→工具调用参数→AI 回复” 的完整链路，定位是 “用户输入理解错了” 还是 “工具调用参数错了”。

如果只拼接进 Prompt 而不存储，这些关键信息会随推理结束而消失，出问题后根本无法溯源。

4. 多端同步 / 多 Agent 协作

  • 多端同步：用户在手机端和电脑端登录同一个账号，需要看到相同的对话历史，这就需要从数据库拉取chat_message表的数据；
  • 多 Agent 协作：比如 “调试 Agent” 处理完报错后，把结果交给 “文档 Agent” 生成报告，“文档 Agent” 需要从数据库读取之前的对话记录（用户需求、报错信息、调试结果），而不是依赖临时拼接的 Prompt。

5. 数据分析 & 模型优化

  • 统计用户高频问题（比如 “超分模型报错” 出现多少次），优化 Agent 的提示词；
  • 分析 Agent 回答的准确率（对比用户问题和 AI 回复），调整模型参数（温度 /top_p）；
  • 挖掘工具调用的高频场景（比如 “代码解释器” 被调用的次数），优化工具配置。

这些分析都需要长期存储的结构化数据，临时拼接的 Prompt 完全做不到。

6. 个性化 & 上下文复用

比如用户 A 经常问 “超分模型部署” 相关问题，系统可以从chat_message表检索该用户的历史对话，生成个性化的回答（比如记住用户的服务器环境、常用框架），而不是每次都从零开始。

knowledage_base 表

知识库，就是RAG，在必要的时候，通过RAG的方式把相关背景信息临时提供给模型

==> 代表系统私有知识，不是模型记忆的一部分

document 表

RAG原始素材层的核心表，主要记录一些文档的二进制信息，不存储原始文档

==> 原始文档一般存在对象存储oss里面

chunk_bge_m3

  • embedding（向量）：只用于相似度检索阶段，是 “检索钥匙”，目的是快速找到和用户问题相关的文本切片

  • content（切片文本）：才是最终拼进 Prompt 的内容，是 “检索结果”，目的是给模型提供私有知识库的上下文

chunk_bge_m3表的embedding字段，本质是为检索阶段提供 “匹配依据”，而非直接输入模型。

==> chunk_bge_m3表是 “中小规模场景的简化版”，本质是把 “业务属性 + 向量 + 文本” 都放在了 PostgreSQL 里，减少系统复杂度。

💡 当切片数量超过 10 万，PostgreSQL 的 ivfflat 索引检索速度会下降，此时会采用 “混合存储” 方案，而不是抛弃 SQL 表：

存储位置 存储内容 核心作用
chunk_bge_m3（SQL 表） id、kb_id、doc_id、content、metadata、created_at 存储业务属性 + 原始文本，负责 “按业务规则过滤”（如只查近 3 个月的切片、只查某知识库的切片）
ES/Milvus（向量库） id、embedding 存储向量 + 切片 ID，负责 “高速相似度检索”
