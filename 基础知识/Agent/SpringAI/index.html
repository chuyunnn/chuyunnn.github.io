当系统中有不止一次模型调用、不止一个agent、不止一个模型的时候，怎么把agent接入系统，作为一种可配置、可切换、可扩展的基础设施？

SpringAI 在 Agent 系统中的角色

在没有框架的情况下，每接入一个模型，你都需要自己处理：

  • HTTP 请求构造
  • 鉴权与重试
  • 不同模型的参数差异
  • 工具调用协议差异

这些工作并不困难，但它们不属于 Agent 的核心逻辑。

💡 Spring AI 把 “和模型交互” 这件事抽象成了一套统一的接口，让你可以把精力放在 Agent 的行为设计上，而不是模型厂商的细节上。

在 Agent 系统中，我们只关心一件事：给我一个可以用来和模型对话的对象。

而这个对象就是 Spring AI 中 ChatClient。

在系统里使用模型

在 Agent 系统中，我们约定，每一个可用的模型，对应一个 ChatClient 对象

==> ChatClient 是对 “模型能力” 的封装，它屏蔽了模型调用的细节，只暴露统一的对话接口

我们为每个模型创建一个独立的 ChatClient Bean：

一个模型 ≠ 一个 Agent：模型是 Agent 的 “对话能力组件”，Agent 是包含模型、工具、状态、知识库的完整智能体

  • ChatClient 是模型的 “标准化封装层”：屏蔽不同模型的调用差异，给 Agent 提供统一的对话接口

  • Agent 是更高层的封装：整合 ChatClient（模型能力）+ 工具调用 + 状态管理 + RAG 检索，实现端到端的智能交互

ChatClientRegistry 模型注册中心

当系统中存在多个 ChatClient 后，下一个问题自然出现了，在运行时，如何根据 Agent 的配置，选择正确的模型？

💡 答案是：不要写 if /switch，而是交给 Spring。

Spring 会自动把所有 ChatClient 类型的 Bean 注入到一个 Map 中，Key 为 Bean 名称，Value 为实例本身

这一小段代码，实际上解决了一个非常重要的工程问题：

  • 新增模型，不需要改任何调度代码：新增一个bean，ChatClientRegistry 会自动将其纳入注册表，无需修改任何调度逻辑
  • 模型注册是声明式的，而不是控制流式的：通过@Bean注解声明，而不是if-else
  • 模型选择完全由数据驱动

在 Agent 系统中，这种 “注册表模式” 是多模型支持的核心。

模型统一抽象成ChatClient，实现多模型在系统中共存，Agent能够自由切换模型，模型接入和Agent行为解耦
