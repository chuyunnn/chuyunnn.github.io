Agent落地-总

Created2026-03-02|Updated2026-03-02|基础知识Agent
|Post Views:

从前端的一次输入开始

整个流程的起点非常普通，用户在聊天输入框中敲下一段文字，按下回车。

在前端看来，这一步并没有任何 “Agent” 的概念，它只做三件事：

  1. 如果当前还没有会话，先创建一个会话
  2. 创建一条 用户消息
  3. 把这条消息立刻渲染到聊天列表中

也就是说，前端不会等待 AI 的任何结果

这是一个非常重要的设计点，用户输入的那一刻，系统就应该 “立刻有反应”

具体流程是这样的：

  1. 用户输入并回车
    • 前端立刻渲染用户消息到聊天列表，让用户看到 “我发了这句话”
    • 同时发起异步 HTTP 请求（或 WebSocket）到后端，携带用户消息和会话 ID
  2. 前端等待响应期间
    • 聊天列表中，在用户消息下方显示一个 “AI 正在思考” 的占位元素 ==> 让用户感知到系统已经收到消息，正在处理
  3. 后端处理并返回结果
    • 后端执行 Agent Loop（Think → Execute → 循环），生成最终回答
    • 最终回答通过 HTTP 响应或 WebSocket 消息推回前端
  4. 前端更新 UI
    • 收到后端返回的 AI 回答后，前端把 “AI 正在输入” 的占位替换成真实的回答内容
    • 如果是流式输出（SSE/WebSocket），则会逐字 / 逐句更新，让用户看到 “打字机效果”

后端接收消息

当 /api/chat-messages 被调用时，后端 Controller 并不会启动 Agent，也不会去调用模型，而只是做两件事：

  • 把用户消息持久化到数据库
  • 发布一个 “聊天事件”（事件就是一个异步消息，用来**解耦 “消息创建” 和 “执行 Agent 逻辑”** 这两件事）

这个事件里包含三样东西：

  • agentId
  • sessionId
  • 用户输入内容

到这里，HTTP 请求就结束了。

把处理所需的所有必要信息都打包带走，让后续处理可以完全独立进行

也就是说，用事件之后就变成了：

  1. Controller 只做两件事：存消息 + 发事件，请求立刻返回，前端不用等 ==> 立即有反馈
  2. 另外有一个事件消费者（比如消息队列的 Worker）在后台监听事件，收到后才启动 Agent 处理 ==> 解耦，能扛并发

[!NOTE]

返回了一个chatMessageId ==> 用于异步追踪：前端拿到 chatMessageId 后，可以通过 WebSocket 或轮询接口（如 /api/chat-messages/{id}），用这个 chatMessageId 去获取最终的 AI 回答

事件

事件监听器是异步任务：监听器不运行在 Web 线程（处理 HTTP 请求的线程）里，而是一个独立的异步任务

  • 这意味着：无论 Agent Loop 跑多久、调用多少工具，都不会阻塞前端页面，用户可以继续操作

事件发布 ==> 让事件监听器处理

到这里，系统正式启动了一个Agent对象

每次用户提问，都会重新“现场组装”一个全新的 Agent 实例

Agent 不是一个单例，也不是长期存活的对象。

在创建过程中，系统会做几件非常重要的事情：

  • 从数据库加载 Agent 的配置
  • 根据配置选择对应的 ChatClient
  • 从数据库中恢复最近的对话历史：当前 sessionId 对应的、本次用户提问之前的所有聊天记录
  • 解析当前 Agent 允许使用的工具
  • 解析当前 Agent 允许访问的知识库

也就是说，这个 Agent 一出生，就已经拥有了完整的上下文环境。

[!IMPORTANT]

Agent 是 “无状态” 的（用完即销毁），它本身不记得之前聊过什么。恢复对话历史有两个关键作用：

  1. 提供上下文（记忆）：让 Agent 知道 “我们之前聊到哪了”。比如用户先问 “什么是多态”，再问 “举个例子”，Agent 必须拿到上一轮的问题，才能给出正确的代码示例。
  2. 填充 Prompt：这些历史会被组装进 Think 阶段的 Prompt 中，作为模型决策的依据（这就是你之前问的 “Prompt 里的上下文”）。

[!CAUTION]

好处：

  1. 无状态，更可靠

    • Agent 不长期驻留内存，每次用完就销毁，避免了内存泄漏、状态混乱等问题

    • 即使 Agent 执行过程中崩溃，也不会影响下一次请求，因为下一次会重新创建

  2. 上下文永远是最新的：每次创建时，都会从数据库重新加载最新的配置、工具、知识库和对话历史

    • 这意味着：如果中途修改了 Agent 的配置（比如新增了一个工具），下一次用户提问时，新的 Agent 就会立刻生效，不需要重启服务

  3. 资源利用更高效：只有在需要处理用户消息时，才会创建 Agent，空闲时不占用资源

    • 对于高并发场景，这种按需创建的方式可以更好地利用系统资源

Think：决定 “接下来该干嘛”

在 think() 阶段，Agent 会做一件非常明确的事情：判断下一步是否需要调用工具。

此时系统会构造一个 Prompt，其中包含：

  • 当前的对话历史
  • Agent 的系统提示词
  • 可用工具列表
  • 可访问的知识库说明

模型的输出，可能是一段普通的 Assistant 回复，或者一个（或多个）Tool Call。

不管是哪一种，这个输出都会被立刻持久化到数据库和放入 “待推送列表”，然后通过 SSE 推送给前端。

Execute：工具才是 “动手的人”

如果 Think 阶段发现了工具调用，Agent 会进入 Execute 阶段。

在这个阶段系统会根据 Tool Call 的描述，直接执行对应工具。

工具执行完成后，会生成 ToolResponseMessage。这些工具返回结果同样会被持久化，通过 SSE 推送到前端，写入对话历史。

对 Agent 来说，工具返回的结果就是 “新的上下文”

消息并不是立刻推的

Agent 在运行过程中，并不会每生成一条消息就立刻推送，而是先统一保存到 pendingChatMessages，在合适的时机一次性推送。

这样做的好处很明显：

  • 避免高频 SSE 发送
  • 保证消息顺序

另外一个原因是我们不能保证每次循环，模型只调用一个工具调用。

SSE 的作用

SSE 在这里承担的角色非常清晰：

  • 不负责业务
  • 不负责状态
  • 只负责把消息 “推过去”

后端只要知道一个 chatSessionId，就可以把消息精准地送到对应的前端页面。

而前端只需要监听不同的 type：

  • 状态类消息 → 更新加载动画
  • 内容类消息 → 插入聊天列表

两边并不共享任何内部结构，只通过事件类型和 payload 通信。

前端并不知道 Agent 的存在

站在前端视角看，这一整套流程非常 “干净”。

它只知道三件事：

  1. 我发送了一条消息
  2. 服务端在不断推送新消息
  3. 最终会告诉我 “结束了”

至于：

  • Think / Execute
  • Tool / RAG
  • Agent Loop

这些都被完整地隐藏在系统内部。
