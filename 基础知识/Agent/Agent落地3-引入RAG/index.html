Agent落地3-引入RAG

Created2026-03-02|Updated2026-03-02|基础知识Agent
|Post Views:

RAG不是模型能力，是系统能力

在这里没有把RAG设计成特殊的模型模式，而是把RAG当成一个工具

💡 因为在 Agent 的世界里，RAG 和 “查天气”“查日期” 没有本质上的区别：

  • 都是模型发现自己不知道
  • 都是通过工具向系统请求信息
  • 都是拿到结果后继续推理

Agent 视角下的一次 RAG 调用

从 Agent 的角度看，一次完整的 RAG 流程如下：

  1. 用户提出问题

    ↓

  2. Agent 判断：我是否需要查阅知识库？

    ↓

  3. Agent 调用 KnowledgeTool

    ↓

  4. 系统执行向量检索

    ↓

  5. 返回相关文档内容

    ↓

  6. Agent 基于内容生成最终回答

Agent 最关心的一件事，是现在缺的背景信息。

从RAG中查询内容流程

  • 用户提问（往往缺少背景信息）
  • 对用户问题进行 Embedding 【向量化】
  • 使用用户问题的向量在向量数据库中执行向量相似度检索
  • 检索到的 Top-K 条 chunk，会被作为补充上下文，与用户原始问题一起发送给大模型
  • 模型基于用户问题和检索到的知识片段生成最终回答并返回给用户

这一步的本质是：RAG 负责 “找对信息”，AI 负责 “说清楚信息”

[!NOTE]

1️⃣ 检索到的 Top-K chunk 会被放在 Prompt 中「SystemMessage（可选）之后、用户原始问题之前」的位置，且会明确标注 “参考文档”，让模型知道这是补充的背景信息，而非用户的提问或历史对话。

2️⃣ 如果担心用 UserMessage 封装 chunk 会让模型误解为 “用户输入”，可以用「自定义 Message 类型」或「直接拼接在 SystemMessage 末尾」

以下位置会导致模型理解混乱，绝对不要用：

  1. chunk 放在用户问题之后：模型先看到问题，再看文档，容易遗漏关键信息
  2. chunk 无标识直接拼接：模型无法区分 “文档内容” 和 “用户问题”，比如直接写 “Java 中的 String 是不可变的…Java 中的 String 为什么是不可变的？”
  3. chunk 混入历史对话：历史对话是用户和模型的交互，混入文档会导致 Token 浪费 + 逻辑混乱

KnowledgeTool

Agent 并不会直接调用 RagService，它只认识一个工具：

  1. RAG 被封装成一个标准工具（KnowledgeTool）
  • Agent 不直接操作底层的 RagService（向量检索服务），而是通过一个名为 KnowledgeTool 的工具来访问知识库。
  • 这符合 Agent 的统一设计：所有外部能力（查天气、查日期、查知识库）都被封装成 ToolCallback，Agent 只需要通过工具名和参数来调用。
  1. 工具的核心逻辑
  • knowledgeQuery 方法接收两个参数：kbsId（知识库 ID，用于区分不同的知识库）和 query（用户的问题 / 检索词）

调用 ragService.similaritySearch 执行向量相似度检索，得到 Top-K 的文档片段（chunk） ==> 将这些片段用换行符拼接成一个字符串返回，作为工具的执行结果

  1. 为了让 Agent 在 Think 阶段能够正确判断是否要使用 RAG，我们会在提示词中明确告诉它：
  • 当前允许访问哪些知识库
  • 每个知识库的大致用途

这些信息并不会被模型 “记住”，但会在当前决策中起到非常关键的引导作用。

一旦模型意识到：“这个问题我可以通过知识库解决”，它就会主动选择调用 KnowledgeTool。

[!IMPORTANT]

告知模型 “可用知识库” 和 “可用工具” 的提示词，都集中在 Think 阶段的 SystemPrompt（也就是「落地2.md」提到的 thinkPrompt）中

一个提示词模板：

关键说明：

  1. 知识库信息：放在 SystemPrompt 的开头，明确 “有哪些库、能解决什么问题”，让模型快速匹配用户问题和知识库；
  2. 工具信息：紧跟知识库信息，明确 “有哪些工具、参数是什么、能做什么”，让模型知道 “该调用哪个工具、传什么参数”；
  3. 决策规则：最后给出判断逻辑，引导模型按规则选择是否调用工具。

💡 这里是thinkPrompt + toolCallbacks 双重告知的方法

为什么需要 “双重告知”？

  • SystemPrompt 解决 “该不该调、调哪个” 的问题（业务逻辑）
  • toolCallbacks () 解决 “怎么调、传什么参数” 的问题（技术规范）

两者缺一不可，否则模型要么 “不知道什么时候调”，要么 “调的时候参数错误”。
