tokens

Tokens == 令牌，是大语言模型处理文本的基本单位，消耗的token数量直接关系到成本、性能和限制

是文本被切分后的小片段

  • 对于英文：大约1个token = 0.75个单词
  • 对于中文：大约1个token = 1-2个汉字

比如：”你好，世界！” 可能被切分为 ["你", "好", "，", "世", "界", "！"] 共6个tokens

统计token数量？

1. 成本控制

绝大多数云AI服务（OpenAI、DeepSeek、智谱等）按token收费

  • 公式：总费用 = (输入tokens + 输出tokens) × 单价

2. 性能限制

所有模型都有上下文窗口限制（比如128K tokens），如果输入+输出的tokens超过这个限制，请求会失败

==> 需要监控使用量，避免超出限制

3. 使用量分析

平均每次对话消耗多少tokens？

优化提示词：减少不必要的tokens可以节省成本

实践注意事项

  1. 输入tokens通常比输出tokens多：输入包含：系统指令、对话历史、工具描述、RAG检索内容等

  2. 工具描述本身消耗tokens

    • 每个工具的name、description、parameters都会计入输入
    • 工具越多，每次调用的基础tokens越多

  3. RAG会增加token消耗

    • **检索到的文档片段**会插入到prompt中

    • [!NOTE]

      ==> 需要平衡：检索精度 和 token成本

  4. 流式响应时的token计数：即使是流式输出，最终也会返回完整的usage统计

    • 可以实时估算消耗，及时终止高消耗请求

一次请求、响应过程

1️⃣ 请求json：

模型看到的是整个message，虽然这里只有一条，但是真实是有上下文的

==> 也就是“历史记忆”，就是把历史会话再一次发给模型

2️⃣ 响应json：

包装在一个完整的message里面

生成文本在content里面 ==> 模型输出本来就可以追加回messages，作为下一轮会话的上下文

[!CAUTION]

通过一个数组手动维护上下文

多轮会话的“记忆感”完全来源于系统对messages的管理，而不是模型的能力

role

可以把 role 理解成对话里的 “身份牌”，它告诉大模型 “这段话是谁说的、是什么性质的内容”，而不是给人看的标签

  • user（用户）：你自己说的话，比如 “生命的意义是什么？”
  • assistant（助手）：模型给你的回答，比如 “这是一个古老而深刻的问题…”
  • system（系统）：给模型的 “后台指令”，比如 “你是一个专业的哲学家，回答要简洁深刻”，它不是对话的一部分，而是模型的 “行为准则”
  • tool（工具）：当模型调用计算器、搜索引擎等工具后，工具返回的结果，必须用这个身份告诉模型 “这不是用户说的，是工具返回的数据”

工具调用

可以为系统定义一系列的工具，然后把这些能力告诉模型（定义tools，在请求中一起发送给模型）

Agent 里的工具定义分为两部分：

  • 工具本身的代码实现：代码实际执行功能
  • 工具描述（Prompt / 结构化 Schema）：模型理解 “有什么工具、怎么用”
    • 用自然语言 + 结构化 Schema（JSON/OpenAPI 规范）告诉模型：工具名、功能描述、入参（参数名 / 类型 / 是否必传 / 含义）、出参格式，这是模型决策是否调用、怎么传参的依据

整体： 定义工具→向模型声明工具→模型决策调用→执行工具→结果回传给模型

  1. 向模型声明工具：把工具 Schema（或框架封装的工具集合）传给模型，同时在 System Prompt 中告诉模型可以调用工具解决问题，调用格式按 Schema 来

  2. 用户提问，模型决策：用户输入问题（如 “北京今天天气怎么样？”），模型分析问题后

    • 判断需要调用get_weather工具
    • 按 Schema 返回结构化调用指令（如{"name":"get_weather","parameters":{"city":"北京"}}）

    [!NOTE]

    也就是模型响应“希望调用的工具”，而不是回答结果

  3. 程序解析并执行工具：Agent 程序解析模型返回的调用指令，找到对应的执行函数，传入参数执行，得到工具结果（如 “北京实时天气：晴，温度 - 2℃，风力 2 级”）

  4. **结果回传给模型**：把工具执行结果按role: tool（或框架指定的格式）回传给模型，模型结合结果生成最终回答

  5. 多轮迭代：如果工具结果不完整（如用户问 “北京和上海的天气差多少？”，模型先调用 get_weather 查北京，再查上海，最后计算差值），模型会重复 2-4 步，直到能回答用户问题。

[!NOTE]

回看整个流程：

  • 模型从头到尾都没有 “直接做事”
  • 它只是不断判断：现在还缺什么信息
  • 每一步缺失的信息，都由系统通过工具补齐

这正是工具调用的本质协作方式：模型负责决策，系统负责执行，而 messages 记录全过程。

注意事项

  • description 描述要精准，避免模糊：description是模型判断是否调用的核心，比如查天气工具要写清【支持中文城市、实时天气、不支持国外城市】，否则模型会传错参数
  • 入参要简洁，尽量少必传：模型处理复杂入参容易出错，工具入参优先用字符串/数字/布尔值，非必要的参数设为可选并加默认值
  • 做参数校验和异常处理：工具执行函数必须过滤非法入参（如计算器过滤特殊字符）、捕获异常（如 API 调用失败、查不到数据），否则 Agent 会直接崩溃
  • 工具单一职责：一个工具只做一件事（如查天气只查天气，不做温度计算），模型更容易理解和调用，复杂功能可以拆分成多个小工具，由模型组合使用
  • 使用结构化调用，拒绝纯自然语言：纯自然语言让模型描述调用（如 “我要调用查天气工具，城市是北京”），程序解析成本高，而结构化 Schema（JSON）让模型返回固定格式，程序直接解析
