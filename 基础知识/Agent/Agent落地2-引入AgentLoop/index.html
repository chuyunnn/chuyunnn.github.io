Agent落地2-引入AgentLoop

Created2026-03-02|Updated2026-03-02|基础知识Agent
|Post Views:

在聊天功能的前提下，引入Agent Loop，让agent开始具备：

  • 判断是否需要外部能力
  • 主动发起工具调用
  • 根据工具结果推进任务

💡 根本问题：这一次模型回复是不是最终答案？ ==> 如果不是，系统介入，推进下一步

首先，新增的字段有：

  1. List<ToolCallback> availableTools
  • 含义：Agent 当前可调用的外部能力列表。
  • 作用：Agent 在对话中判断需要调用工具时，会从这个列表中选择合适的工具
    • 这里的 ToolCallback 是每个外部工具的封装，包含工具的名称、描述、参数定义和执行逻辑
  • 示例：比如列表中包含 WeatherToolCallback、CalculatorToolCallback，Agent 就可以根据用户提问，决定调用 “查天气” 或 “做计算”
  1. ToolCallingManager toolCallingManager
  • 含义：统一执行工具调用的协调器
  • 作用：
    • **解析模型返回的工具调用请求**（如函数调用指令），从 availableTools 中找到对应的 ToolCallback
    • 执行工具的具体逻辑，并将工具**返回**的结果整理成模型能理解的格式，再交给模型进行下一步处理

是 Agent 实现 “思考 → 调用工具 → 整合结果再回答” 这一闭环的核心组件

  1. ChatOptions chatOptions
  • 含义：显式控制模型行为的配置项
  • 作用：
    • 用于覆盖或精细化模型的调用参数
      • 如 temperature（温度，控制随机性）、maxTokens（最大生成长度）、topP（核采样）、stopSequences（停止词）等

相比 V1 中可能硬编码的参数，V2 通过 ChatOptions 实现了参数的可配置化和可复用性，让 Agent 的行为更可控

  1. ChatResponse lastChatResponse
  • 含义：保存最近一次模型输出，作为执行阶段的输入
  • 作用：
    • 在工具调用流程中，模型第一次输出的可能不是最终答案，而是一个工具调用指令（如 {"name": "getWeather", "parameters": {"city": "北京"}}）。
    • 把第一次的 ChatResponse 保存下来，当工具执行完成后，Agent 会结合工具结果和这个历史响应，再次调用模型生成最终回答

它是实现多轮工具调用和上下文延续的关键状态存储

执行流程控制

SpringAI的原生模型支持 模型->自动执行工具->回填结果 的流程，这里把它关掉了，对执行过程进行控制

一旦工具被自动执行，Agent 将失去：

  • 记录执行轨迹的能力
  • 插入中断、回滚、重试的机会
  • 对 “是否继续” 的判断权

功能划分概览：

  • Think（决策模块）：负责分析当前对话上下文与系统状态，判断下一步行动策略
  • LLMs（大语言模型）：根据 Think 阶段给定的决策约束与上下文信息，生成结构化的推理结果，包括普通回复或带有工具调用描述的输出
  • Execute（执行器）：负责解析并执行 LLMs 生成的工具调用请求，将真实执行结果以标准化形式回注到对话历史中

三个部分之间交互预览：

  • Think → LLMs：生成策略与行为规划
  • LLMs → Execute：输出动作描述与工具调用请求
  • Execute → Think：反馈执行结果并更新系统状态

这个循环会持续运行，直到任务被明确标记为完成，或者超过循环最高次数限制

Think 阶段

决定：“下一步干什么” ==> 不是给用户回答，而是做决策

然后是模型调用：

这里发生的三件事：

  1. 使用完整的上下文（chatMemory）
  2. 暴露所有可用工具
  3. 获取完整 ChatResponse，而不是直接取文本，因为 ChatResponse 包含了工具调用的内容

⚠️ 其中：

  1. .prompt(prompt) 中的 prompt：一个完整的 Prompt 对象
  • 包含「对话上下文（历史消息）+ 本次用户提问 + 可能的默认系统提示」等所有基础内容

作用：提供模型决策所需的**全部对话上下文**，是 Think 阶段的 “事实依据”

  1. .system(thinkPrompt) 中的 thinkPrompt：一段纯文本字符串，专门作为「SystemMessage（系统提示词）」覆盖 / 补充到上述 Prompt 对象中
  • 内容：是给模型的 “决策指令”（比如 “你是决策模块，决定是否调用工具”），是 Think 阶段的 “规则约束”

作用：定义模型在 Think 阶段的角色和决策规则，让模型专注于 “做决策” 而非 “直接回答用户”

ToolCall 出现时，为什么不立刻写入 memory？

Think 阶段结束后，做了一个预防 bug 的处理：

也就是说：

  • 没有工具调用 → 这是最终回复 → 写入 memory
  • 有工具调用 → 暂不写入 → 交给 execute () 统一处理

💡 这一点非常重要。如果把 “带 tool_calls 的 AssistantMessage” 提前写入 memory，而后面工具执行失败或缺失，会导致上下文不一致

1️⃣ 中间指令不作为上下文：不浪费token

2️⃣ 工具执行失败（最常见）

假设用户问 “查北京今天温度”，模型生成工具调用指令后，你提前写入 memory，然后工具执行失败（比如天气接口报错）：

  1. 提前写入的错误上下文（memory 中的内容）
  2. 工具执行失败：无法获取温度，需要模型重新决策（比如提示 “接口异常，无法查询”）
  3. 模型下次读取 memory 时，会看到 “自己已经发了工具调用指令”，但没有后续的 “工具执行结果 / 最终回答”，会产生两个问题：
    • 模型误以为 “工具已经调用成功”，继续追问 “温度结果呢？”，但实际根本没结果
    • 或模型重复生成相同的工具调用指令，陷入 “调用失败→重复调用” 的死循环

如果不存memory：

模型读取 memory 时，只看到 “用户要查温度”，完全不知道 “之前生成过工具调用指令”（因为没写入 memory），它会基于 “用户的原始需求” 重新决策：

  • 既然工具执行失败，就直接生成 “失败提示” 给用户，而非纠结 “为什么工具调用没结果”
  • 不会重复生成工具调用指令，因为 memory 中没有 “我已经发过指令” 的记录

  • 写入了工具调用指令 → 模型认为 “我已经做了这个决策”

  • 没写入 → 模型完全不知道 “自己曾经生成过工具调用指令”，只会基于用户的原始提问重新思考

    • 只看到请求和结果，不会重复指令

Execute阶段：系统真正动手的地方

Agent 从 “会想” 走向 “会做” 的关键步骤

  1. 取出带 tool_calls 的 AssistantMessage
  2. 根据 name + arguments 执行工具
  3. 生成 ToolResponseMessage
  4. 返回完整的新对话历史

step：Think + Execute 的最小「循环」单元

一次 step = 一次决策 +（可选的）一次执行

chat () 方法，已经不再是 “一次调用”

在 V2 中，chat() 方法已经发生了语义变化：

这不再是 “问一句，答一句”，而是：给 Agent 一个目标，让它自己跑完

MAX_STEPS 的存在，也清晰地表达了一个工程态度：

  • Agent 不应该无限循环
  • 模型的推理深度是有上限
  • 系统必须兜底

总结

这样我们就有了一个Agent loop，后面无论是加RAG还是其他东西，都是在这个loop的基础上加层
