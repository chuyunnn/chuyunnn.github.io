一个完整的 Prompt 本质是 List<Message>，包含三类消息（按顺序）：

Message 类型 作用 对应 Prompt 位置
SystemMessage 系统提示（模型人设） 最前面（固定）
历史 UserMessage 之前的用户提问 系统消息后，按时间排序
历史 AssistantMessage 之前的 AI 回复 对应用户消息后
最新 UserMessage 本次用户提问 最后面（当前请求）

❗️ 因为token跟整个 Prompt（包含系统提示、历史提问、历史回答、当前提问） + 回答 都有关

关于消耗token数量：（对于主流大模型）

常用简体中文：1 字 = 1 token

中文标点（，。！？；：）：1 个 = 1 token

生僻字 / 特殊符号 / Emoji：1 个 = 1~2 token

英文 / 数字：1 个单词 / 串 = 1~2 token

1. 把“长回答 / 长提问 / 历史消息” 塞进 Prompt，就会消耗对应 Token

MessageWindowChatMemory 的核心价值，就是通过限制历史消息数量，控制 Prompt 总长度，从而控制 Token 消耗

🙋 如果提问、回答很长，会整个塞进prompt里面吗？

：会！默认情况下，只要没做特殊处理，历史长提问会完整塞进 Prompt；

如果想避免大量token消耗，有 3 种主流处理方式（按优先级排序）：

处理方式 核心逻辑 适用场景
1. 滑动窗口（最常用：限制上下文数量） 只保留最近 N 条消息（MessageWindowChatMemory） 大多数普通聊天场景
2. 消息摘要（性价比高：控制每条上下文的长度） 调用模型生成：把长历史消息 / 长回答总结成短文本，只带摘要进 Prompt 单条消息很长（如几百字）
3. 上下文压缩（进阶） 用 Spring AI 提供的 ContextCompressor 自动精简上下文（保留关键信息）：基于当前提问筛选关键上下文 专业场景（如客服、知识库）

2. 和JSON的关系？

ChatMemory 提取的上下文，先组装成 Prompt（Spring AI 上层概念），再由 Spring AI 把这个 Prompt 完整序列化成 JSON 请求体（底层传输格式）

其中，SystemMessage、UserMessage、AssistantMessage等完整序列化成 JSON 的 messages 数组中的不同部分

3. systemPrompt会在对话一开始的时候放进chatMemory中

💡 确保每次组装prompt的时候，都出现在最前面

SystemPrompt（系统提示词）是给 AI 模型的 “全局指令”

==> 用来定义模型的角色、行为准则、回答风格、知识范围等，是整个会话的 “底层规则”，优先级高于用户的提问

类型 示例 SystemPrompt
角色定义 “你是一个专业的 Java 编程导师，只用简洁的语言回答编程问题，不聊无关内容。”
格式要求 “所有回答必须以 markdown 格式呈现，代码片段需要加语言标识，比如```java。”
约束规则 “拒绝回答任何违法、暴力、色情相关问题，遇到此类问题直接回复‘无法回答’。”
知识范围 “你的知识仅限于 2024 年之前的 Java 技术，不回答 2024 年后发布的新框架相关问题。”
个性化风格 “你的回答要像朋友聊天一样轻松，带一点点幽默，但不要过度调侃。”

由于 MessageWindowChatMemory 是按 “消息数量” 截断，建议把 SystemPrompt 排除在滑动窗口的计数外（否则可能被截断）

4. 新增/修改systemPrompt怎么做？

1️⃣ 替换原有 SystemPrompt：最常用的方式，直接更新 SystemPrompt，后续组装 Prompt 时用新的规则

2️⃣ 追加systemPrompt：在原有规则上补充（比如新增 “回答要带示例”）

合并成一个，模型读取「唯一的全局指令」，按合并后的规则执行

3️⃣ 动态添加到 ChatMemory：不建议把多个 SystemPrompt 存入 ChatMemory（会导致规则混乱），但如果必须这么做，需要确保最新的 SystemPrompt 在最前面

多个独立的系统指令，模型读取「多个全局指令」，可能出现规则冲突 / 优先级模糊

🙋 如果新的systempromt和原来的有冲突，会怎么判断呢？

  • 多SystemPrompt场景：靠运气
    • 如果发给模型的 messages 数组里有多个冲突的 SystemMessage（比如一个要求 “简洁”，一个要求 “详细”），模型的处理逻辑是：
      • 优先级模糊：模型不会严格按 “最后出现的规则” 执行，也不会按 “最先出现的”，而是根据训练数据的 “偏好” 随机选择（比如 GPT 可能优先遵循 “详细”，讯飞星火可能优先遵循 “简洁”）
      • 规则稀释：冲突规则会互相抵消，模型可能既不简洁也不详细，只给出 “折中但不符合预期” 的回答
      • 极端情况：模型会忽略所有冲突规则，只按默认行为回答（相当于 SystemPrompt 失效）
  • 单 SystemMessage 场景（替换 / 合并）：模型 “按文本顺序执行，后补充的规则优先级更高”
    • 如果是一个完整的 SystemMessage 里包含冲突内容（比如 “回答要简洁，且回答要详细带代码示例”），模型会：
      • 优先遵循 “后出现的规则”（比如 “详细带代码示例” 会覆盖 “简洁”）；
      • 尽量 “折中执行”（比如回答详细但控制篇幅，或简洁但加一行代码）；
      • 无法折中时，会忽略矛盾的部分，只执行能落地的规则（比如只带代码示例，不管简洁要求）。

总结上述三种方式：只有 “完全替换” 能彻底规避冲突风险

处理方式 是否有冲突风险 核心原因
存多个 SystemMessage ✅ 高风险 模型无明确优先级，随机执行
合并冲突规则到一个 ✅ 中风险 模型会折中 / 忽略，无法完全按预期执行
完全替换原有 SystemPrompt ❌ 无风险 模型只接收唯一规则，无冲突

🙋 新增的系统提示词比较简短，怎么补充基础内容呢？

实际场景中，动态新增的 SystemPrompt 往往是 “临时规则”（比如 “本次回答用 markdown”），而基础内容（角色、核心约束）需要保留，核心思路是：把 “基础规则 + 临时规则” 合并成一个无冲突的完整 SystemPrompt，具体分 3 步：

步骤 1：拆分 SystemPrompt 结构（便于动态拼接）

步骤 2：会话中新增简短临时规则（无冲突）

步骤 3：会话中新增冲突规则（完全替换）
